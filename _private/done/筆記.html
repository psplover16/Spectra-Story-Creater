Spectra 速查筆記

📚 本文件使用說明

  • 一般段落 = AI 整理的速查資料（流程、指令、設定檔、模式說明）
  • 💡 心得 = 個人踩過的坑、Codex vs Claude Code 的差異觀察
  • 快速查指令？ → 三、主要 Slash Commands 與 四、Spectra CLI 指令

一、開發流程（標準路徑）#

              ┌─────────────────────────────────────────────┐
              │                                             │
[想法]──→ /spectra-discuss ──→ /spectra-propose ──→ /spectra-apply ──→ /spectra-archive
            (討論釐清)        (產出四份文件)        (依任務實作)        (歸檔)
                                                       ↑
                                                       │ 中斷後
                                                       └─ /spectra-ingest（恢復上下文）
  • discuss 可以省略：需求很清楚時，可直接進 propose
  • apply 跑到一半被打斷：下次回來先 ingest，再繼續 apply
  • archive 之後，change 會被移出 openspec/changes/，成為正式規格的一部分
  • 白話講：changes 是「這次要改什麼」的變更單，specs 是「系統目前正式長什麼樣」的主規格

change 的三種狀態#

狀態意思適合的時機
parked（備忘）文件寫好了，但還沒動工propose 完、人工檢查中、暫時不想做
active / in-progress正在實作apply 期間
archived（封存）完成且歸檔全部任務做完。proposal / design / spec / tasks 都已走完

💡 個人心得：Codex vs Claude Code 在 park 行為上不一樣

Codex 會混亂 — /spectra-propose 產出會跑到 .git/ 裡，想看必須先 unpark。 而 unpark 在「正規 spectra」只是改 park 狀態旗標，Codex 卻會整個搬資料夾位置。

這是 Codex 整合的非正規行為，正規 spectra（Claude Code 整合）不會把檔案寫到 .git/。

二、四份產出文件（artifact）#

0. 名詞先釐清：proposal vs artifact#

很多人會把這兩個詞搞混，其實是不同層級

  • artifact（製品） = spectra 工作流中產出的「文件檔案」的總稱。/spectra-propose 一次會產出 4 個 artifact。
  • proposal = 是其中一份特定的 artifact（檔名 proposal.md），是 4 份裡的「企劃書」。

簡單說：proposal 是 artifact 的一種，artifact 是上位概念。一份 change 的 4 個 artifact = 1 個 proposal + 1 個 spec（每個 capability 各一份）+ 1 個 design + 1 個 tasks。

1. 文件位置#

/spectra-propose 會產出四份文件，但實際位置不要硬猜，要以 Spectra 回傳的 changeDir 為準。

  • 可用 spectra status --change <name> --json
  • 或 spectra instructions apply --change <name> --json
  • 直接看其中的 changeDir

常見情況：

  • 一般可見 change（Claude Code 正常情況）：openspec/changes/<change-name>/
  • Codex 環境下、且被 park 的 change：.git/spectra-app/changes/<change-name>/（這是 Codex 整合的非正規行為，正規 spectra 不會把檔案寫到 .git/）

1-1. changes 與 specs 的關係#

這兩個最容易混淆，但角色其實不同：

  • openspec/changes/<change-name>/ = 這次 change 的工作區
  • openspec/specs/<capability>/ = 目前已接受、正在生效的正式規格

可以直接這樣理解：

  • changes 在回答：這次想改什麼
  • specs 在回答：系統現在正式應該怎麼運作

changes 裡也會看到 specs/<capability>/spec.md，但那份是這次 change 的 delta spec，不是主規格本體。它描述的是「這次變更想新增 / 修改哪些規格」。

真正長期存在的正式規格在：

  • openspec/specs/<capability>/spec.md

流程上通常是：

  1. 在 openspec/changes/<change-name>/ 裡先產出 proposal / design / tasks / delta spec
  2. apply 完成後驗證
  3. archive 時，把這次 change 的 spec 內容同步進 openspec/specs/<capability>/spec.md
  4. 之後 changes 是歷史變更單，specs 則成為新的正式基準

用 Git 比喻：

  • changes 很像 PR / 變更提案
  • specs 很像 merge 後主分支上的正式內容

2. 四份文件總覽#

順序檔名角色類比回答什麼語言
1proposal.md企劃書為什麼要做？要改什麼？影響哪些檔案？跟 .spectra.yaml 的 locale
2specs/<capability>/spec.md驗收標準做完後使用者應該看到哪些「行為」？必須英文，用 SHALL/MUST
3design.md技術設計文件技術上怎麼做？主要設計決策是什麼？跟 locale
4tasks.md施工清單要拆成哪些實作步驟？跟 locale

3. 四份文件的依賴關係#

proposal.md  ─┬─→ specs/<capability>/spec.md     (依 proposal 的 Capabilities 一個一個產)
              │
              └─→ design.md  ──→  tasks.md       (tasks 依 design 拆步驟)

後面的 artifact 會讀前面的當輸入，所以 propose 過程是有順序的，不是同時生成。

4. 每份文件的詳細用途#

4-1. proposal.md — 企劃書（為什麼 + 要改什麼）

整個 change 的「總綱」，是其他三份文件的根據。

依 change 類型有不同模板：

  • Feature（新功能）：Why / What Changes / Non-Goals / Capabilities（New/Modified）/ Impact
  • Bug Fix（修 bug）：Problem / Root Cause / Proposed Solution / Success Criteria / Impact
  • Refactor（重構）：Summary / Motivation / Proposed Solution / Alternatives Considered / Impact

最重要的章節是 Impact

  • Modified：只能填磁碟上真的存在的檔案
  • New：填要新增的檔案
  • Removed：要刪除的檔案

apply 階段會用 Impact 做 preflight 檢查，亂填會被擋下來。

4-2. specs/<capability>/spec.md — 驗收標準

  • 每個 capability（能力）一份 spec，所以可能不只一份
  • 描述「行為」而不是「實作」
  • 寫 Given / When / Then 的 scenarios，要可驗證
  • 必須用英文寫，動詞用 SHALL / MUST 這種規範語氣（不是建議，是規範）
  • archive 之後，這份 spec 會被合併進主規格 openspec/specs/<capability>/spec.md，成為長期保存的正式規格

4-3. design.md — 技術設計

proposal 講「做什麼」，design 講「技術上怎麼做」。通常包含

  • 架構選擇（為什麼用 X 而不是 Y）
  • 資料模型 / store 結構
  • 元件 / 模組劃分
  • 與現有程式碼的整合方式
  • Alternatives Considered（其他方案為什麼不採用）

寫給「未來的實作者」（包括下一個接手的 AI agent）看的，避免他們反推設計意圖。

4-4. tasks.md — 施工清單

把 design 拆成可一步步執行的具體任務。

  • 格式：- [ ] 任務描述（待辦） / - [x]（完成）
  • 可選 [P] 標記（例：- [ ] [P] 任務）代表可以平行做
    • 只有當 .spectra.yaml 設了 parallel_tasks: true 才會生效
  • /spectra-apply 會一項一項執行勾選
  • 健康的 tasks.md 標準：
    • 每個任務 1 小時內可做完
    • 全部任務不超過 15 條
    • 不跨超過 3 個不相關子系統
    • 超過就應該拆成多個 change

.spectra.yaml 重點#

這是整個 spectra 工作流的總開關，控制 AI 產出 artifact 的語言、apply 階段的行為、worktree、TDD 等。所有可用欄位

# 規格資料夾位置（OpenSpec 主資料夾）
# 預設：openspec
# 改路徑要重建向量索引（rebuild vector search index）
spec_dir: docs/specs

# AI 產出 artifact 的語言
# 你目前用：tw（繁體中文）
# 例外：specs/*/spec.md 永遠英文（規範文件需要 SHALL/MUST）
locale: tw

# === Workflow toggles（功能開關）===

# TDD 模式：apply 時先寫測試再寫實作（Red → Green → Refactor）
tdd: true

# Audit 模式：apply 完自動跑安全/危險預設值審查
audit: true

# 平行任務：tasks.md 裡 [P] 標記才會真的平行執行
parallel_tasks: true

# 額外產生 /spectra:X 形式的 slash command（除了 /spectra-X）
claude_slash_commands: true

# === Git Worktree（隔離分支）===

# 為每個 change 開獨立 git worktree，避免互相干擾
worktree: true

# worktree 自訂位置（預設 .spectra/worktrees）
worktrees_dir: .spectra/worktrees

# === Claude Code skill 強度 ===

# low / medium / high / xhigh / max
# 越高 → 思考越久、品質越好、token 越貴
claude_effort:
  apply: high

# === 對哪些 AI 工具產生指令檔 ===

tools:
  - claude
  - cursor

你目前實際的設定（.spectra.yaml）只有開了 locale: tw，其他都還是註解狀態。

欄位你目前狀態建議
locale: tw✓ 已開保持（中文 artifact 用）
tdd: true✗ 註解中想用 TDD 流程才開（見 第八節）
audit: true✗ 註解中想要每次 apply 完自動安全審查才開
parallel_tasks: true✗ 註解中想讓 tasks 的 [P] 標記真的平行才開
worktree: true✗ 註解中你目前 git 是壞的（.git 結構錯），先把 git 修好再說
claude_effort: apply: high✗ 註解中apply 階段如果常常拆得不好可以開 high 試試

改 .spectra.yaml 後要不要重啟？

  • 改 spec_dir → 要重建向量索引（檔案開頭就有警告）
  • 改其他開關 → 下次跑 slash command 時會直接生效，不用重啟

openspec/config.yaml 重點#

schema: spec-driven

context: |
  專案類型：日語學習網站
  技術棧：Vue 3 + TypeScript + ...

rules:
  proposal:
    - <規則 1>
  specs:
    - <規則 1>
  design:
    - <規則 1>
  tasks:
    - <規則 1>

注意：

  • rules 只有 proposal / specs / design / tasks 四個鍵會被讀
  • 寫其他頂層鍵不會生效

六、典型一次完整流程#

整個流程分三個階段：準備 → 規劃 → 實作。讀的時候只看你目前在的階段就好。

[準備期]                  [規劃期]                       [實作期]
                                                         ┌──→ 中斷恢復 ─┐
repo preflight ──→ scaffold ──→ discuss ──→ propose ──→ apply  ←───────┤
                                  │           │                         │
                                 (可選)    (人工檢查)                ──→ archive

階段 1：準備期（確認骨架）#

目的：避免到了 /spectra-apply 才發現整個 app 骨架不存在。

# 0. repo preflight：看 repo 是哪一種狀況
rg --files -g "package.json" -g "src/**" -g "vite.config.*" -g "vitest.config.*" -g "tsconfig*.json"

#    A. 已有完整骨架        → 可直接 discuss 功能、在既有架構上 propose
#    B. 只有部分骨架        → propose 時把缺的骨架一起寫進 change
#    C. 幾乎只有文件 / 空 repo → 先單獨開一個 scaffold change

# 0-2. 如果是 B 或 C，先建前端骨架（一個獨立 change）
/spectra-discuss 我要先建立 Vue 3 + TypeScript + Vite 的前端 app 骨架
/spectra-propose 建立 Vue 3 + TypeScript + Vite 前端骨架，包含 router、基本頁面結構、測試設定
/spectra-apply add-web-app-scaffold

階段 2：規劃期（討論 → 產出 4 份文件 → 人工檢查）#

這階段是最重要的防呆關卡，artifact 寫錯會在 apply 階段一次爆給你看。

# 1. 需求還不夠清楚時，先 discuss
/spectra-discuss 我想做一個錯題本功能
# 或讀指定檔案
/spectra-discuss 請讀取指定 Markdown 檔案 `@/_private/discuss.txt` 的內容，並以它作為唯一輸入。最終把結果放入 @/_private/propose.md

# 2. propose 前先對齊需求和 repo 現況（防呆）
#    - proposal.md 的 Impact -> Modified：只能寫真的存在的檔案
#    - proposal.md 的 Impact -> New：寫即將新增的檔案
#    - 沒 package.json、src/、router、App.vue → 不能當「既有 app」
#    - 缺骨架時要先決定：
#      (1) 先開一個 scaffold change
#      (2) 還是把 scaffold 納入同一個 change

# 3. 產出四份文件
/spectra-propose 加上錯題本：答錯的題目自動加入錯題本，使用者可以重做
# 或讀指定檔案
/spectra-propose 請讀取指定 Markdown 檔案 `@/_private/propose.md` 的內容，並以它作為唯一輸入。
# → 產出 `<changeDir>/{proposal,design,tasks,specs/...}.md`

# 4. 人工檢查 4 份文件
#    - proposal.md 的 Impact -> Modified 檔案真的存在嗎？
#    - proposal.md 的 Impact -> New 合理嗎？
#    - design.md 建立在真實 repo 結構上嗎？
#    - tasks.md 是否假設了不存在的 router、page、store、test setup？
#    - spec.md 的能力名稱和 proposal 對得上嗎？
#
#    💡 propose 預設會自動 park，所以 `spectra list` 看不到 change
#       要看用 `spectra list --parked`
#       要打開資料夾來檢查文件可以先 unpark：
spectra unpark <name>
spectra unpark add-down-stairs-game

階段 3：實作期（apply → 中斷恢復 → archive）#

# 5. 開始實作
/spectra-apply add-down-stairs-game
# → 如果 apply preflight 跳出 missing files：
#    - 先判斷是 proposal / design / tasks 寫錯，還是真的缺 app scaffold
#    - 不要硬做，回頭修 artifacts 或調整 change scope

# 6. 中途被打斷 / 隔天回來
/spectra-ingest add-down-stairs-game     # 補回上下文
/spectra-apply add-down-stairs-game       # 繼續實作

# 7. 全部完成後歸檔
/spectra-archive add-down-stairs-game

六之一、/spectra-apply 之後要再修改怎麼辦？#

兩個選擇

選擇 A：在原本的 change 上補修改（推薦小改）

# 用新的 discuss 補需求
/spectra-discuss 請讀取指定 Markdown 檔案 `@/need/discuss2.md` 的內容，並以它作為唯一輸入。

# 把新需求併進現有 change 的 tasks
/spectra-ingest add-down-stairs-game

# 繼續 apply 新增的 task
/spectra-apply add-down-stairs-game

選擇 B：另開一個新 change（推薦大改 / 不同 capability）

/spectra-discuss <新需求>
/spectra-propose <新需求>
/spectra-apply <new-change-name>

判斷標準：

  • 跟原 change 同一個 capability 的小調整 → A
  • 新 capability / 跨多檔案的大改 → B（避免單一 change 失控）

六之二、避免下次再犯同類錯誤的最小檢查清單#

  • 在 /spectra-propose 前，先確認 repo 是既有 app、半成品 app，還是幾乎空 repo
  • Impact -> Modified 只能填目前磁碟上真的存在的檔案
  • Impact -> New 才能填目前不存在、準備新增的檔案
  • 不要把 context 裡的技術背景誤當成 repo 已經存在的骨架
  • discuss 負責收斂需求，propose 必須對齊 repo 現況，apply 不應該才第一次發現骨架不存在
  • apply preflight 一旦出現 missing files，先修 artifacts 或 scope，不要把錯的假設直接帶進實作

七、踩坑提醒#

依主題分組，遇到哪一類問題就看哪一段。

7-A. Repo 現況對齊（最常踩）#

  • 不要把 proposal 的技術背景直接等同於 repo 目前現況
  • Modified 路徑必須先確認真的存在，不能靠猜
  • propose 前先用 rg --files -g "package.json" -g "src/**" ... 確認 repo 是 A/B/C 哪一種

7-B. 檔案位置（不要硬猜路徑）#

  • 不要預設 /spectra-propose 產物一定在 openspec/changes/，先看 Spectra 回傳的 changeDir
  • 拿 changeDir 的方法：spectra status --change <name> --json 或 spectra instructions apply --change <name> --json
  • 在 Codex 環境，parked change 可能跑去 .git/spectra-app/changes/<change-name>/（詳見 九、Codex vs Claude Code 行為對照）

7-C. 語言／語氣（artifact 的語言不一致）#

  • specs/*/spec.md 必須英文，動詞用 SHALL / MUST（規範語氣，不是建議）
  • proposal.md / design.md / tasks.md 會跟 .spectra.yaml 的 locale 走

7-D. 編碼（中文 artifact 容易出包）#

  • 中文 artifact 要確保 UTF-8 編碼
  • 避免 PowerShell 或 CLI 管線把中文寫成「問號字元」
  • 避免 BOM 汙染可見文字（AGENTS.md 也有提到）

7-E. 設定相依（開關沒打開 → 功能不會生效）#

  • tasks.md 裡的 [P] 標記只有在 .spectra.yaml 開 parallel_tasks: true 才會真的平行
  • TDD 流程只有在 tdd: true 才會啟用（見 八、TDD 模式）

7-F. 指令行為（容易誤解的地方）#

  • /spectra-ask 的答案只能來自 openspec/，不是一般知識問答（不是 ChatGPT）
  • /spectra-propose 產出後自動 park，是設計、不是 bug — spectra list 看不到，要 spectra list --parked

八、TDD 模式#

1. 什麼是 TDD#

TDD = Test-Driven Development（測試驅動開發）

紀律：先寫測試，再寫實作。寫程式的順序倒過來。

1. Red（紅）   ─→ 先寫一個失敗的測試（功能還沒做，所以紅）
2. Green（綠） ─→ 寫最少的程式碼讓測試通過（變綠）
3. Refactor   ─→ 在測試保護下重構，保持綠燈
                 ↓
              （回到 1，下一個小功能）

2. 跟一般寫法的差別#

一般寫法TDD
順序寫程式 → 寫測試（常忘）寫測試 → 寫程式
測試覆蓋率容易漏自然就高
程式設計品質容易寫成難測試的形狀被迫寫成可測試（鬆耦合、純函式）
改 code 心理怕壞掉有測試擋著、敢改

3. 在 spectra 怎麼啟用#

打開 .spectra.yaml 的這行（拿掉 #）

tdd: true

不用重啟，下次跑 /spectra-apply 就會走 TDD 流程。

4. 啟用後 /spectra-apply 會怎麼變#

沒開 TDD（預設）：

讀 tasks.md → 直接寫實作 → 跑測試（如果 tasks 有要求）→ 勾選任務

開了 TDD：

讀 tasks.md → 先寫一個失敗的測試 → 跑測試（紅）
            → 寫最少實作讓測試通過（綠）
            → Refactor（保持綠）
            → 勾選任務

每一條 task 都會走一次 Red→Green→Refactor 的小循環。

5. 跟你專案的關係（Vue 3 + Vitest）#

你專案已經裝好 vitest.config.ts，TDD 模式跑出來的測試會直接放進 vitest。

適合 TDD 的部分

  • 純邏輯（題目評分、錯題本累積、卡片狀態機、計時器邏輯）
  • composable / store（pinia store 的 mutation/getter）
  • utility 函式
  • 修 bug（先寫一個會重現 bug 的測試）

不太適合 TDD 的部分

  • UI 視覺 / CSS 動畫（很難用斷言描述「看起來對」）
  • 第一次探索的 prototype（連需求都還沒定，沒法寫測試）
  • 純串接外部 API 的薄層（如果只是 fetch 包一下，測試價值低）

6. 跟 .spectra.yaml 其他開關的搭配#

同時開效果
tdd: true + audit: trueapply 走 TDD + 完成後跑安全審查（最嚴格）
tdd: true + parallel_tasks: true平行 task 各自走自己的 Red→Green→Refactor（有可能互相干擾，要小心）
tdd: true + claude_effort.apply: highapply 思考更久但會把 TDD 紀律走得更完整

7. 何時不該開#

  • 趕時間做 demo / spike：TDD 慢，原型期不適合
  • 純樣式調整：寫不出有意義的測試
  • 既有 code 沒測試基礎，第一次大改：先補上測試骨架（一次性），再開 TDD 做後續

8. 建議#

你這個錯題本 / 練習網站專案，邏輯比例高（評分、累積、狀態），開 TDD 收益不錯。建議的試法

  1. 先在筆記裡記住「打開 tdd: true」這個動作
  2. 下次有純邏輯的 change（例如「自動加入錯題本」），把 tdd: true 打開試一個 change
  3. 對比有開 vs 沒開的 task 拆解、測試覆蓋率，自己判斷要不要常駐打開
  4. 純樣式 change 之前，把它關回去（避免被迫寫很彆扭的視覺測試）

九、Codex vs Claude Code 行為對照#

兩個工具都可以跑 spectra，但行為有差異。Claude Code 是正規行為，Codex 整合有些非正規的 quirk，會混亂。

9-1. 主要差異對照表#

項目Claude Code（正規）Codex（非正規）
自動讀取的指令檔CLAUDE.md（你目前沒有）AGENTS.md（你有）
Slash command 格式/spectra-propose/spectra-propose（一樣）
propose 產出位置openspec/changes/<name>/一般 change 也是 openspec/changes/<name>/
parked change 位置還在 openspec/changes/<name>/，只改 DB 標記會搬到 .git/spectra-app/changes/<name>/（bug 行為）
unpark 行為只改 DB 標記，檔案不動會把資料夾從 .git/... 搬回 openspec/changes/...
.spectra.yaml 開關都吃都吃
TDD / audit 等模式都支援都支援

9-2. 規則檔的雙工具相容（重要）#

你目前 AGENTS.md 寫的規則（繁中、UTF-8、檔案存取限制等）

  • ✅ Codex 會自動讀
  • ❌ Claude Code 不會自動讀（會讀的是 CLAUDE.md）

要讓兩邊都生效，建議

# 建一個 CLAUDE.md，內容只寫一行 @AGENTS.md
echo "@AGENTS.md" > CLAUDE.md

這樣

  • Claude Code 自動讀 CLAUDE.md → 引用 AGENTS.md ✅
  • Codex 自動讀 AGENTS.md ✅
  • 只維護一份規則（在 AGENTS.md），不會分裂 ✅
